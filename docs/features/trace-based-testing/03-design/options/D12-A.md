## Option A: Build the watch seams in v1, unexposed   (stance: most extensible)
Summary: v1 builds the internal pieces that v1.1 needs: a per-span property evaluator, a span-graph resolver, a property-extraction mode, and repro fields with an expect-fail self-check. v1's `always`/`never` run through the same per-span code. No flag or CLI surface ships. v1.1 then adds only the `SpanClosed` consumer, the stderr line and the `--watch` flag.

How it works:
- `internal/praytest/property.go`: `Property{Kind Always|Never; Sel selector.Selector; Pred starlark.Callable; Pos Position}` and `PropertyEval{thread; props}` with `Observe(ctx, sp tui.CheckSpan, g SpanGraph) []Failure`. In v1, `expect.always/never` = `Select` + `Observe` for each match, so batch and live share one predicate path.
- `SpanGraph` interface (`Parent(sp)`, `Root(sp)`, which return `(CheckSpan, bool)`). The span's Starlark binding resolves `span.parent`/`span.trace` through it. `CheckView` implements it with D1's indices. Live, an unresolved parent is `None` (D7 item 5 already allows this).
- `internal/render/tui/check.go`: D1's `toCheckSpan` plus unexported `(*Model).spanAt(trace, span)` for O(1) per-close lookup.
- `(*Case).Properties(ctx)`: runs `check` in a `collect` phase where `always`/`never` register a `Property`, other `expect.*` do nothing, and `run.one` stops the check.
- D8: `Recording.Repro *ReproOrigin{PropertyPos; Failure}`, plus `SelfCheck(..., ExpectFail)`, both tested and never called from the CLI.
- `BenchmarkObserve` (10 properties x 10k spans) in `make bench-diff`, so v1 gets an early M5 reading.

Steelman: A2 is cheapest to test when v1.1 is a thin wrapper around code that is already tested. Routing v1's `always`/`never` through `Observe` means every v1 file run exercises the watch path. The resolver forces the live/post-drain `parent` difference into the open now, not after release. The benchmark shows whether M5 is reachable before anyone commits to v1.1.

Pros: little v1.1 rework. One predicate path, so no second implementation that can drift. M5 risk is visible early. Everything is internal, so it adds no R9 surface.

Cons / failure modes / hidden costs:
- About 600-900 LOC plus tests, most of it with no v1 user. This is R8 scope creep.
- Collect mode has D5's data-dependence hole: properties after a `run.one` are never found. It ships a phase rule that nobody has validated.
- `SpanGraph` puts an interface indirection in every v1 span access, and live semantics now shape the v1 binding.
- A thread reused per span may hit the step cap, which counts cumulatively (D6 step 6). Untested.
- The interfaces are guessed before the M5 design. If M5 forces a different model (an `internal/tracemodel` store, per D1's revisit), they get rewritten anyway.

Criteria scores:
- v1 cost added (30): 2 - M-sized internal work that only the batch `always`/`never` path uses.
- Rework avoided (30): 4 - evaluator, resolver, extraction and repro are ready, but the guesses may not survive M5.
- v1 semantics not constrained (20): 2 - the binding goes through a live-aware resolver and adds a collect phase.
- M5 headroom (10): 4 - early benchmark and per-span path with no per-call view copy.
- Cheap to abandon (10): 2 - dead code can be deleted, but the resolver is woven into the v1 binding.

Cost: M     Reversibility: easy for the unexposed pieces; hard for the `SpanGraph` binding once the v1 tests depend on it.

Unknowns / assumptions: Starlark step-cap behaviour on a long-lived thread. Whether watch needs properties outside `check` at all. Whether `Observe` reaches 20us p99 without a span index. Whether D6/D7 accept a resolver in place of slice indices.
