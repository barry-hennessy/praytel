## Option B: Dagger-backed `make trace-test`, a required job in check.yml, and a separate nightly workflow   (stance: most conventional)
Summary: Do what the repo already does for every check. `make trace-test` calls a Dagger function that builds `praytel` and `shop` inside the pinned Go image and runs the S5 command. `check.yml` gets one more job shaped like `lint`. A new `trace-nightly.yml` workflow reruns the same target with `COUNT=20`, and a manual dispatch of it with `COUNT=100` produces the M2 evidence.

How it works:
- `dagger/tracetest.go` adds `TraceTest(count int = 1, gomaxprocs string = "")`, marked `+cache="never"` (as at `dagger/check.go:39`). Without that marker Dagger would return a cached result for identical repeats. The function builds on `goContainer` (`dagger/main.go:78-85`). It builds `/usr/local/bin/praytel` and `/usr/local/bin/shop` (`shop` is its own module, `demo/workloads/shop/go.mod`) and apt-installs `zsh` for the M8 test. It runs `go test -run Shell ./internal/testrun` once. Then it loops `praytel test --grpc-port=0 --http-port=0 testdata/traces` `count` times under `set -e`, printing `run i/N` before each run. Cases call `shop` from PATH.
- Makefile: `trace-test:` runs `$(DAGGER) call trace-test $(if $(COUNT),--count $(COUNT),) $(if $(GOMAXPROCS),--gomaxprocs $(GOMAXPROCS),)`, next to the golden targets (`Makefile:180-220`).
- `check.yml`: add a `trace-tests` job with the same steps as `lint` (`.github/workflows/check.yml:27-40`), plus `timeout-minutes: 15` (from D2's consequences). It has no `continue-on-error` and no path filter, because a path-filtered required check stays pending forever. The header comment gets `make trace-test` (lines 1-12). The `golden` job (lines 77-120) is not touched.
- `trace-nightly.yml`: runs on a daily cron and on `workflow_dispatch` with a `count` input (default 20) and `gomaxprocs`. It runs `make trace-test COUNT=…` and uploads the log as an artifact.
- Ubuntu only. No workflow in `.github/` uses a matrix or macOS.
- Rollout: one PR adds `shop -card` (A5), the cases, the target and both workflows. The author dispatches the nightly workflow on the branch with `count=100, gomaxprocs=1` and links that run in the PR. An admin then marks `trace-tests` as required (A7), recorded as a CONTRIBUTING step.

Steelman: A contributor already knows this pattern. Locally and in CI the tests run in the same pinned container, so "works on my machine" mostly goes away. No new tooling or concepts are added. Each piece copies a working precedent: the `lint` job shape, the never-cache marker from `vulncheck`, and the artifact upload from `bench.yml:86-90`.

Pros: very close local/CI parity. New test files are picked up through the directory argument. The golden job is untouched. The 100-run evidence is reproducible from a link. Easy to delete.

Cons / failure modes / hidden costs:
- `dagger call` reduces every non-zero exit to an error. The 1/3/4/130/143 distinction (D10) is lost in the job's status, and the S4 report shows up inside Dagger's error output, which may be truncated. This is unverified.
- The tests run in a nested container on a shared 2-vCPU runner. The time margin is 450ms against 200ms, and the Dagger engine competes for CPU, so the M2 evidence describes a noisier environment than a laptop.
- Every PR pays for Dagger engine startup plus two builds. The 100-run dispatch takes several minutes.
- A failed scheduled run only notifies through GitHub's default email. Nothing opens an issue, so drift can go unnoticed (M7).
- `make trace-test` needs Docker and Dagger locally. A bare `praytel test testdata/traces` on the host fails unless `shop` is on PATH.

Criteria scores:
- Determinism and flake resistance: 4. Pinned image, no caching, no retries, a timeout and GOMAXPROCS evidence; the deduction is for nested-container CPU noise.
- Local/CI parity: one command: 5. Both run the same `make trace-test`, the same Dagger function and the same image.
- Diagnosable red runs: 3. The report reaches the log only through Dagger's error output, and exit codes are collapsed.
- New test files need no CI edit: 5. The tests are found by directory expansion.
- CI time and cost: 3. Engine plus builds on every PR; nightly and evidence runs are cheap.
- Golden job untouched and isolated: 5. It is a separate job with no shared state.

Cost: M     Reversibility: easy

Unknowns / assumptions: how Dagger shows a failing exec's stdout in the CI log (needs a check). Whether apt `zsh` in `golang:1.26` should be pinned. Whether a daily cron next to the weekly one (`check.yml:19-20`) is acceptable for Actions minutes.
