## Option A: One Dagger function, one copied job, COUNT for repeats   (stance: minimal change)
Summary: Add one `TraceTest` Dagger function, one `make trace-test` target and a `trace-tests` job copied from `lint`. Repeats for M2 and the nightly run use an optional count passed through the same target. Nothing new in praytel beyond what D2/D10 already fix.

How it works:
- `dagger/check.go`: `TraceTest(ctx, count int /* +optional, default 1 */, gomaxprocs string /* +optional */)`, marked `+cache="never"` so repeats really run. It reuses `goContainer` (`dagger/main.go:78-85`), runs `go build -o /usr/local/bin/ ./cmd/praytel ./demo/workloads/shop` and then a `sh -c` loop of `praytel test --grpc-port=0 --http-port=0 testdata/traces` that stops at the first failure and echoes `run i/N`. `shop` is on PATH, so `env("SHOP_BIN","shop")` defaults work and no case needs `SHOP_BIN`.
- `Makefile` (beside `lint`, `Makefile:169-178`): `trace-test: $(DAGGER) call trace-test $(if $(COUNT),--count $(COUNT),) $(if $(GOMAXPROCS),--gomaxprocs $(GOMAXPROCS),)`. This reuses `COUNT` (`Makefile:42`).
- `.github/workflows/check.yml`: a `trace-tests` job that copies `lint` (`:27-40`) and runs `make trace-test COUNT=${{ github.event_name == 'schedule' && 20 || 1 }}` (passed through `env`, which keeps zizmor happy). Add a second cron line for nightly runs (`:19-20`). No `continue-on-error` and no retry. Any non-zero exit (1, 3 INCOMPLETE, 4) fails the Dagger exec and so fails the job. The `golden` job (`:77-120`) is not edited.
- `demo/workloads/shop/main.go:179-200`: add `-card TYPE` to filter `orders` by card. `-pace` already exists (`:180`).
- M2 evidence: run `make trace-test COUNT=100` and `make trace-test COUNT=100 GOMAXPROCS=1` (locally or by `workflow_dispatch` on the branch, `:21`) and paste both tails into the PR.
- A7: an admin marks `trace-tests` as required after the merge.

Steelman: CI and local runs execute one identical command in one pinned image (`dagger/main.go:22`). The diff is about 40 lines and follows a pattern three jobs already use. Directory discovery (D10) means new `*.praytest.star` files need no edits. Proving determinism uses the same code path that gates PRs, not a separate harness.

Pros: smallest surface. Parity by construction. The golden job is untouched. Easy to delete.

Cons / failure modes / hidden costs:
- The new cron line also triggers lint, vulncheck, zizmor and golden every night. That costs extra minutes, and golden now runs on a schedule even though its definition is unchanged. Avoiding it means adding `if:` guards to other jobs.
- Output from a red run reaches the log through Dagger's exec error and is wrapped in TUI noise. S4 diagnosability depends on Dagger printing stdout and stderr in full.
- The loop stops at the first failure, so you get no flake rate, only pass or fail.
- A repeat loop inside one container hides variation between runners. The 100 runs share one host's timing.
- The Dagger engine cold start (minutes) adds to every PR.
- Nobody gets told when the nightly fails. The red run sits in the Actions tab.
- M8's zsh is not in `golang:1.26`. That is out of scope here, but it will need an apt line later.

Criteria scores:
- Determinism and flake resistance: 3. It follows -pace 0s, exit 3 and no retries, but adds no flake-rate measurement and repeats inside a single container.
- Local/CI parity: 5. CI and local runs use the same `make trace-test` in the same image.
- Diagnosable red runs: 3. The output is present but buried in Dagger error output.
- New files need no CI edit: 5. Discovery is by directory.
- CI time and cost: 3. Each PR pays a Dagger start-up, and the nightly cron triggers every job.
- Golden job untouched: 4. Its definition is untouched, but it now also runs nightly.

Cost: S     Reversibility: easy

Unknowns / assumptions:
- Dagger's exec error carries the full praytel stdout and stderr.
- `+cache="never"` behaves on a function with arguments as it does on `Vulncheck` (`dagger/check.go:39`).
- Ports bound with `--grpc-port=0` work inside the Dagger container.
- `workflow_dispatch` on a branch counts as "in the PR" for M2.
