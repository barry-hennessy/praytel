## Option C: Go-tool dispatch, a `testrun` package, a streaming reporter   (stance: most conventional)
Summary: Dispatch works the way `go`/`git`/`cargo` do: a switch on `argv[0]`, and each subcommand gets its own `flag.FlagSet`. The runner and its report live in a new `internal/testrun` package behind a `Reporter` interface. Output streams one line per case, `go test -v`-style, and ends with one summary line. `cmd/praytel` only wires the pieces together.

How it works:
- **Dispatch** (`cmd/praytel/main.go:63-75`): `runProcess` checks `argv[0] == "test"` → `runTest`. Otherwise it calls today's `args.Parse`, unchanged. Before that, if `argv` has no `--` and `"test"` appears in it, it returns a usage error with the hint `put flags after "test"`. Those argv are already `ErrUsage` today (`args.go:90-93`), so no valid invocation changes.
- **Parsing**: `args.ParseTest(argv, errOut) (TestConfig, error)` uses `flag.NewFlagSet("praytel test", ContinueOnError)`. A shared `registerRun(fs)` defines grpc/http-port and drain-idle/drain-timeout, so the defaults are the same as the root flags (`args.go:105-108`). `TestConfig{Mode (Files|Record; Watch in v1.1), Paths, RecordFile, Command, Ports, Drain}`. `--tui` and `--snapshot` are defined only so that they can be rejected. The `--` rules are checked per mode.
- **Usage errors**: a new `args.UsageError{Msg}` that `Is(ErrUsage)`. `newErrMapper` (`main.go:46-49`) prints `praytel: <Msg>` when Msg is set, and today's line otherwise.
- **`internal/testrun`**:
  - `Expand(args) ([]string, error)` handles the S3 rules and is pure.
  - `Run(ctx, lt, files []*praytest.File, rc RunCaseFunc, rep Reporter) Summary`.
  - `RunCaseFunc func(ctx, *praytest.Case) CaseOutcome` is injected, because D2's `runCase` stays in `cmd/praytel` and an internal package cannot import `main`.
  - `Reporter{File(path); Case(name, Outcome, lines []string); Summary(Summary)}`. `TextReporter` prints S2/S3 bytes, plus `INTERRUPTED`/`not run`.
  - `Summary.Code()` gives `max(0,3,4)`, with 128+signo overriding it (D2 step 7).
- **Flow in `runTest`**: `Expand` → `praytest.Load` on every file, collecting every `UsageError` (D5) → print them and exit `1` → only then the loop starts. JUnit/TAP would be another `Reporter` behind a later flag. Neither is built in v1, because the vision does not ask for it.

Steelman: This is the shape every Go CLI reader recognises, and it needs no dependency. Each layer can be tested on its own: `Expand` is a pure table test (M8), `Run` runs against a fake `RunCaseFunc` with a golden `bytes.Buffer` (M6), and `ParseTest` is a table test like `args_test.go`. Streamed results show progress during 10-minute cases in CI.

Pros: The root path is untouched. `--watch` is just one more `Mode`. A machine-readable format can be added without touching the runner.

Cons / failure modes / hidden costs:
- A `Reporter` interface with one implementation is speculative.
- On an exit mismatch, `flag`'s own errors (`flag provided but not defined`) are not prefixed with `praytel:`. Captured child output goes to stderr and can interleave with streamed stdout in CI logs.
- The tracing rule extends to a new package (`CONTRIBUTING.md:42-45`).
- The `RunCaseFunc` indirection splits the case lifecycle across two packages.

Criteria scores:
- Backward compatibility: 5. Only argv that are already errors change, and only their message.
- Precise usage errors: 4. All errors come before any child. The wording of raw `flag` errors is not controlled.
- Testability: 5. Pure expander, fake runner, golden reporter.
- Package boundaries: 4. `cmd` is thin, but `runCase` is injected from `main`.
- Extensible: 4. Per-subcommand FlagSet plus a mode enum. Dispatch is a switch, not a registry.
- No new dependencies: 5. Standard library `flag` only.

Cost: M     Reversibility: easy (internal APIs only; the CLI surface is fixed by the vision)

Unknowns / assumptions: D2's `runCase` signature can be adapted to `RunCaseFunc`. Streaming output order is acceptable for the S3 goldens.
