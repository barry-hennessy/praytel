## Option B: Guardrails only, no new v1 code   (stance: minimal change)
Summary: v1 adds no interface, type or phase for watch. D12 records three "do not break" rules that v1 tasks and reviewers must follow, plus a v1.1 plan note. Everything watch needs that is not already in D1/D6/D7/D8 is v1.1 work.

How it works:
- **v1 rules (go into task acceptance notes, no new code):**
  1. Keep D1's unexported `toCheckSpan(*spanView) CheckSpan` as a separate function used by `CheckView`/`Settle` extraction. Do not inline it.
  2. `internal/selector` stays free of Starlark and of `CheckView` (D7 item 10, already enforced by depguard). `Matches(CheckSpan)` must not read sibling spans.
  3. `(*Case).Check(ctx, CheckView)` stays callable without a child process or `caseResult` (D6/D8). The `always`/`never` builtin keeps its selector and its predicate as separate values on `checkState` and does not fold them into one closure.
- **v1.1 plan note (non-binding):** watch folds events into a `tui.Model` with no bubbletea program. On `SpanClosed` it builds one `CheckSpan` through `toCheckSpan`, filters it with `Matches`, and calls the predicate on a reused per-goroutine Starlark thread. Properties are found by running each `check` against a collector `run` (D5 "Revisit"). If the collector cannot find all properties, v1.1 adds D5's additive Collect phase. When `Parent`/`Trace` are `-1` at close, `None` is passed and the difference is documented. Repros use D8's `Generate`/`SelfCheck`/`WriteNew` with v1.1's `Recording` fields and expect-fail mode.

Steelman: A2 is unvalidated, and M5 cannot be measured until watch exists. The seams that matter (one fold, a per-span `CheckSpan` builder, a pure matcher, an in-memory check entry point) were already paid for by D1, D6, D7 and D8 for their own v1 reasons. Anything more would be guessing at a design that has not been benchmarked. Each item in the v1.1 plan is additive.

Pros: no v1 code, tests or public surface added. v1 post-drain semantics stay as they are. Nothing to delete if A2 fails.

Cons / failure modes / hidden costs:
- The rules are prose. Nothing tests them, so a v1 refactor can inline `toCheckSpan` or merge the selector and predicate without anyone noticing.
- v1.1 still has to build a per-span check entry point, set up and reuse a thread outside D6's fresh-thread-per-check rule, and do property extraction. Collector probing misses properties that sit behind `run.one` or branches.
- A headless fold without bubbletea is assumed, not checked. If `Model.apply` needs the TUI program, D1's M5 revisit (extract `internal/tracemodel`) becomes v1.1 work.
- Nothing is measured, so M5 risk only shows up in v1.1.

Criteria scores:
- v1 cost added for v1.1 (30): 5 - no code, three review rules.
- Rework avoided in v1.1 (30): 3 - fold, matcher, generator and `Failure` are reused; the per-span entry point and property extraction are new.
- v1 semantics not constrained by watch (20): 5 - v1 behaviour does not change.
- Performance headroom for M5 (10): 2 - no headroom work and no benchmark, so it relies on D1/D7 revisit triggers.
- Cheap to abandon if A2 fails (10): 5 - there is nothing to remove.

Cost: S     Reversibility: easy

Unknowns / assumptions: `tui.Model.apply` can run without a bubbletea program. Collector probing finds the common S6 properties. Reusing one Starlark thread per goroutine is compatible with D6's step cap and `checkState`.
