## Option C: Continuous determinism proof in one Dagger container   (stance: radical alternative)
Summary: This option drops the premise that determinism is proven once, in a single PR, and then guarded only by the nightly run. Every `trace-tests` run is itself a repeat run: a `TraceTest` Dagger function builds `praytel` and `shop` into one pinned container and runs the unchanged S5 command N times. Some runs use `GOMAXPROCS=1` and some use the default, and the job fails if any run fails. The per-PR job, the 100-run evidence and the nightly check all use the same target and differ only in N.

How it works:
- `dagger/tracetest.go` (new) adds `func (m *Demos) TraceTest(ctx, repeat int /* +default=5 */) (string, error)` with `+cache="never"`, the same as `Vulncheck` (`dagger/check.go:39-44`). It starts from `goContainer` (`dagger/main.go:78-85`, `golang:1.26` at `dagger/main.go:22`), installs `zsh` for M8, and runs `go build` for `./cmd/praytel` and `./demo/workloads/shop` into `/usr/local/bin`. That puts `shop` on PATH, so cases need no `SHOP_BIN`.
- A Go loop runs `praytel test --grpc-port=0 --http-port=0 testdata/traces` with `Expect: ANY`. Each run gets `WithEnvVariable("TRACE_RUN", i)` so Dagger can't serve a cached result. Odd-numbered runs set `GOMAXPROCS=1`. The loop stops at the first exit that isn't 0 and returns that run's report, prefixed `run 3 of 5 (GOMAXPROCS=1)`. On success it returns `5 of 5 runs passed`. It also runs the M8 table test with `go test`.
- In the `Makefile`, `trace-test: $(DAGGER) call trace-test $(if $(REPEAT),--repeat $(REPEAT),)`. This follows the `golden-check` shape (`Makefile:201-207`).
- `check.yml` gets a new `trace-tests` job that copies the `lint` steps (`.github/workflows/check.yml:27-40`) and runs `make trace-test`. The `golden` job (`:74-120`) is not touched.
- `trace-nightly.yml` (new) runs on a daily cron and on `workflow_dispatch`, with a `repeat` input defaulting to 20. The 100-run evidence is a dispatch with `repeat=100` on the PR branch, and its run URL goes in the PR body.
- Rollout: merge the job and get the 100-run evidence, then an admin marks `trace-tests` as required (A7).

Steelman: Flakiness is found in the PR that adds a flaky case, by the author, before it can block anyone else. A one-off 100-run proof expires with the next commit, and a continuous check doesn't. Local and CI runs share one toolchain, one set of shells and one way of finding `shop`, so "passes on my machine" has a single meaning. There is only one mechanism, so the 100-run evidence and the nightly run can't drift away from the gate.

Pros: hermetic parity; no `SHOP_BIN` handling; repetition logic lives in tested Go, not YAML; new files are picked up through the directory argument.
Cons / failure modes / hidden costs:
- Repeating the suite in the required job makes flakes block more PRs. A case with a 1% flake rate blocks about 5% of PRs, including unrelated ones, which is the risk R7 names.
- `make trace-test` needs Docker and Dagger, and S5's text has it as a plain `praytel test`. That is slower than the native `make golden` precedent (`Makefile:197-198`).
- If the cache-bust is missing, Dagger memoizes the runs and the evidence is fake, with nothing to show it.
- Timing margins (R7) are checked inside nested containers on shared runners, so parity covers the environment but not CPU speed.
- PR CI time grows about N times, on top of the cost of starting Dagger.

Criteria scores:
- Determinism and flake resistance: 3. Flakes are caught early and continuously, but the repetition makes them block more PRs.
- Local/CI parity: 5. Local and CI run the same container and the same command.
- Diagnosable red runs: 3. The S4 report is there, but wrapped in Dagger output with a run prefix.
- New test files need no CI edit: 5. The suite takes a directory argument.
- CI time and cost: 2. Every PR pays for N runs plus Dagger overhead.
- Golden job untouched and isolated: 5. It gets a separate job and workflow.

Cost: M     Reversibility: easy (set `REPEAT=1`, or point the target at native `praytel test`)
Unknowns / assumptions: The `golang:1.26` image has `bash` and `sh` but not `zsh` (assumed). How long one suite run takes is unknown, and it sets N. It is unknown whether D2's drain can tell `GOMAXPROCS=1` and the default apart.
