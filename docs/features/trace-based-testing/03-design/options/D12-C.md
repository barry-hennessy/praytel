## Option C: Watch evaluates whole checks per completed trace, not per span   (stance: radical alternative)
Summary: Drop the premise that watch evaluates `always`/`never` per `SpanClosed`. v1.1 watch runs each case's existing `check` from the watched file against a per-trace `CheckView` once that trace settles, and keeps only `always`/`never` failures that are not `ZeroMatch`. v1 builds no per-span path and no property extraction. It keeps three small invariants so a single trace can be fed to the v1 evaluator.

How it works:
- v1 seam 1 (`internal/render/tui/check.go`): canonical sort and extraction run over any set of `*spanView`, for example `extract(spans []*spanView) CheckView`, so both `Settle` and `Model.CheckView` call it. v1.1 calls it with one trace's spans. Its `Parent`/`Trace` indices are local to that slice.
- v1 seam 2 (D6): `(*Case).Check(view CheckView) []Failure` is a pure function of a `CheckView` and the frozen module. It is re-entrant: a fresh thread per call, no globals, no channel or `Model` argument.
- v1 seam 3 (D6): `Failure.Kind` and `Failure.Builtin` stay. Watch filters on them (`Builtin ∈ {always, never}`, `Kind != ZeroMatch`).
- v1 must avoid: a per-span evaluator, a Collect phase, and any check API that reads `run` lazily from a live model.
- v1.1 adds a settle detector on the live fold. A trace counts as complete when its root is closed and none of its known spans are open for quiet period Q. Child exit flushes any trace still pending. Repro generation is D8's.

Steelman: there is one evaluator and no second semantics. When a trace is evaluated, `span.parent`/`span.trace` are resolved as they are in file runs, so the "`None` live" difference (D1, D7) disappears. Any predicate that passes a file run behaves the same in watch. A repro reproduces exactly what watch saw, because both evaluate whole traces. No Starlark property extraction is needed, and the data-dependence hole in the Collect approach goes away. The v1 cost is about one refactor of the extraction plus tests.

Pros: tiny v1 footprint; parity between file runs and watch; per-trace sort cost is O(k log k) on small k; trivially abandoned.
Cons / failure modes / hidden costs:
- This deviates from the vision text (S6 "as each span closes", §5 Pipeline, M5's "per property per span" metric), so the vision must be amended.
- A violation is reported after its trace settles, not when the span closes. Long-lived or streaming traces may only be reported at child exit.
- Quiet-period heuristics can evaluate a trace too early if a late child arrives, or hold memory.
- `run.one` or `expect.eq` in a watched file can stop a check before its `always`/`never` run. Watch files must be written in an always/never-only style or the restriction documented.
- Each trace pays thread and builtin setup (D6 creates builtins per check). This may break M5 for traces of 1-2 spans.
- Headless watch still imports the TUI model (D1 revisit trigger).

Criteria scores:
- v1 cost added for v1.1: 5 - one extraction refactor and two invariants, no new surface.
- Rework avoided in v1.1: 4 - the evaluator is reused unchanged; the settle detector and filter are new.
- v1 semantics not constrained by watch: 5 - watch adopts v1 semantics; v1 changes nothing.
- Performance headroom for M5: 2 - per-trace setup overhead, and the metric itself must be redefined.
- Cheap to abandon if A2 fails: 5 - the seams are internal refactors with standalone value.

Cost: S     Reversibility: easy (v1 part); the vision amendment is a product decision

Unknowns / assumptions: users accept trace-completion latency (A2 does not cover this); a robust Q exists for the target workloads; per-check builtin setup is below ~20µs; M5 owners accept a per-trace metric.
